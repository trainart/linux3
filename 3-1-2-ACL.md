## ACL (Access Control Lists) 

Linux filesystem permissions are today more than we might generally know.

Basically we know permissions for:
* **U**ser (or user owner)
* **G**roup (or owner group)
* **O**ther (everyone else)

which are:
* **R**ead 
* **W**rite 
* e**X**ecute 

Plus three other attributes SUID, SGID, Sticky Bit.

However modern Linux systems have possibility to use additional **ACL**s (**Access Control Lists**), 
which enable more flexible and granular control over access rights.

ACLs enable to set **additional** permissions for file/directory to individual users or groups
without changing the base ownership and permissions.

ACL is Linux kernel feature and is currently supported by many modern filesystems, including (but not limited to):
* **ext2**, **ext3**, **ext4** 
* **xfs**
* **tmpfs**
* **zfs**
* ... 
<br>



### Install ACL (if not present yet)

With ACL (Access Control Lists) it's possible to set access permission to files or directories more strictly than standard permissions.

> Key Concept: **ACLs OVERRIDE standard permissions!**

In recent Linux versions acl package is already installed.

You can check if it is there with:

```bash
rpm -q acl
```

If you get the package name, it means you have it installed.

If missing, it can be installed with:

```bash
yum -y install acl
```

There are two main commands for ACL management:

* **getfacl** - view ACLs 
* **setfacl** - modify ACLs

### Simple example

Create test directory 

```bash
mkdir /srv/acltest
```

Check initial state

```bash
getfacl /srv/acltest
```

You can see nothing special yet.
It is the same standard permission information, that we can see with 

```bash
ls -ld /srv/acltest
```

Now assign additional ACL to `student`
```bash
setfacl -m u:student:rwx /srv/acltest
```

Check now

```bash
ls -ld /srv/acltest
```

You should notice additional "**+**" sign after `/srv/acltest/` permissions

```bash
getfacl /srv/acltest

```

You should see new line `user:student:rwx`

<br><br>
> REMEMBER ! <br>
> `ls` shows `+` indicator where there is ACL <br>
> So if you see `+`, you might want additionally run <br>
> `getfacl` for that file/directory <br>
> to get REAL permissions picture.
<br><br>


#### Create new file/dir as `student`

Now as user **student** create new directory inside `/srv/acltest/`

```bash
sudo -u student bash -c 'mkdir /srv/acltest/student-dir'
```

Now as user **student** create new file inside `/srv/acltest/`

```bash
sudo -u student bash -c 'echo "Student file" > /srv/acltest/student-file'
```

Check that they belong to `student`

```bash
ls -la /srv/acltest 
```

### Removing ACLs

`-b` option removes all ACLs from file/directory

Run the following to remove all ACLs from `/srv/acltest`

```bash
setfacl -b /srv/acltest
```

Note `+` indicator has gone from directory `acltest`

```bash
ls -la /srv 
```

So user `student` don't have special permission inside `/srv/acltest` directory anymore.

Try as user **student** create new file inside `/srv/acltest/`

```bash
sudo -u student bash -c 'touch /srv/acltest/new-file'
```

But what belongs to the `student` remains.
For example, you can add data to the file `/srv/acltest/student-file`

```bash
sudo -u student bash -c 'echo "Text for student-file"  >> /srv/acltest/student-file'
```

```bash
cat /srv/acltest/student-file
```

Or you can create new file in the directory `/srv/acltest/student-dir`

```bash
sudo -u student bash -c 'echo "Text for file f1"  >> /srv/acltest/student-dir/f1'
```


```bash
ls -la /srv/acltest/student-dir/
```

```bash
cat /srv/acltest/student-dir/f1
```

### ACLs for directories

Create directory `/srv/project2`

```bash
mkdir -p /srv/project2/job{4,5}
```

Set ACL recursively

```bash
setfacl -R -m u:student:rwx /srv/project2
```

**-R** - sets ACL to a directory recursively 


Check

```bash
getfacl /srv/project2
```


```bash
getfacl /srv/project2/*
```

Now try as user **student** run the following:

```bash
sudo -u student bash -c 'mkdir /srv/project2/dirNEW'
```

```bash
sudo -u student bash -c 'echo "TEST NEW" > /srv/project2/fileNEW'
```

Check

```bash
getfacl /srv/project2/*
```

You will see that `/srv/project2/dirNEW` and  `/srv/project2/fileNEW` don't have ACL.
It is because they do not inherit ACL.


Of course we can manually set ACL recursively

```bash
setfacl -R -m u:student:rwx /srv/project2
```

But if we want the inheritance we can use DEFAULT ACL setting, which is separate.

If we want ACL to be inherited inside directory, we should define not only ACL for directory, but also default ACL.

```bash
setfacl -m u:student:rwx,d:u:student:rwx /srv/project2
```

Now if we create new file or directory inside `/srv/project2` it will have the same ACL as `/srv/project2` directory

```bash
sudo -u student bash -c 'mkdir /srv/project2/dirNEW2'
```

```bash
sudo -u student bash -c 'echo "TEST NEW" > /srv/project2/fileNEW2'
```


```bash
getfacl /srv/project2/*
```



### Mask

You may notice `mask` option in output of `getfacl`, what is it for?
(don't mix with `umask`, which is totally different thing).

**Mask** acts as additional/final global permission filter,
ensuring that users or groups **are not granted more permissions than allowed by the mask**.

So for all ACLs **MAXIMUM** of real/effective permissions will be what is allowed by mask
(NOTE! we talk about ACLs, **mask** is not related to basic **rwx** permissions for owner/group/others).

In case we don't specify the mask specifically it will be flexible to allow everything we specified for our ACLs.
But if we will specify that, access will be **not more than** allowed by mask.

If we will run 

```bash
getfacl /srv/acltest/student-dir/f1
```

we will see `mask::rw-`

But let's limit it manually

```bash
setfacl -m m::r /srv/project1/file7
```

```bash
getfacl /srv/project1/file7
```

> NOTICE:
> Real permissions are shown to the right with **#effective:**
>


Now let's fix the mask:

```bash
setfacl -m m::rw /srv/project1/file7
```

```bash
getfacl /srv/project1/file7
```

And try again as `user2` run the following:

```bash
echo "Test3" >> /srv/project1/file7
```

You also should be able to see the contents of `/srv/project1/file7`

```bash
cat /srv/project1/file7
```

But it will not be the same with `student`. 
Why ?




### Resume 

* ACLs allow granular permission control beyond traditional Unix/Linux permissions 
  * with ACL rules we provided separate additional permission to user `student` for directory `/srv/acltest/`
  without touching basic **R**ead, **W**rite, e**X**ecute permissons for **U**ser, **G**roup, **O**ther. 
* Combine `setfacl/getfacl` with traditional `chmod` for comprehensive security
* If you decide to use ACL, document details of your config, as they can become complex to manage

### PRACTICE 2

As `root` create a set of directories and files:

```bash
mkdir /srv/project1
```

```bash
touch /srv/project1/file7
```

```bash
ls -l /srv/project1
```

Check initial ACL list

```bash
getfacl /srv/project1
```

As we can see no special permissions exist initially

Try modifying some file <br>
**as user `student`**

You should not be able to do so.

```bash
sudo -u student bash -c 'echo "Test" > /srv/project1/file7'
```

```bash
setfacl -m u:student:w /srv/project1/file7
```

Check ACL settings to understand

```bash
getfacl /srv/project1/file7
```

Notice added line `user:student:-w-`

Also notice we can see additional ACL are present with `ls -l` too:

```bash
ll /srv/project1/file7
```

NOTE: **[+] is added on attribute**

Now try again  <br> 
**as user `student`**, <br>
it should work now:

```bash
sudo -u student bash -c 'echo "Test2" >> /srv/project1/file7'
```

```bash
sudo -u student bash -c 'echo "Test3" >> /srv/project1/file7'
```


At the same time user `student` can't **see/read** that file

```bash
sudo -u student bash -c 'cat /srv/project1/file7'
```

But `root` can

```bash
cat /srv/project1/file7
```

Why ?

From the above `getfacl` output you may notice:

> `user:student:-w-` <br>
> ... <br>
> `other::r--`

We see that even though all others have **r**, student is specifically mentioned and has only `w`.
Thus permissions of user `student` should be mentioned separately.

Let's fix that.

We can remove all ACLs

```bash
setfacl -b /srv/project1/file7
```

And set new ones <br> 
(NOTE ! Previous removing was not necessary for this, just used to learn `-b` option).

```bash
setfacl -m u:student:rw /srv/project1/file7
```

```bash
getfacl /srv/project1/file7
```

Now try again to **read** that file <br> 
**as user `student`**, <br>
it should work now:

```bash
sudo -u student bash -c 'cat /srv/project1/file7'
```




### PRACTICE 3

Situation:

Web server logs in `/srv/log/nginx` need special access:

* User `nginx-full` - Full access (read/write/execute). In real life it may be Webserver user, like `www-data`
* User `nginx-read` - Read-only access to monitor log files
* User `nginx-write` - Write-only access to modify log files (but not read)
* Others: No access

#### Create users

```bash
useradd nginx-full ; useradd nginx-read; useradd nginx-write
```

#### Create log directory
```bash
mkdir -p /srv/log/nginx/
```

#### Set base permissions
```bash
chmod 750 /srv/log/nginx/
```

#### Set ACLs for specific access needs + default ACLs so new files inherit permissions
```bash
setfacl -m u:nginx-full:rwx,d:u:nginx-full:rwx /srv/log/nginx/  # Full access 
setfacl -m u:nginx-read:r-x,d:u:nginx-read:r-x /srv/log/nginx/  # Read-only access
setfacl -m u:nginx-write:-wx,d:u:nginx-write:-wx /srv/log/nginx/  # Write-only access
```

Here we do two-in-one 

* **u:nginx-full:rwx** — General ACL for directory.
* **d:u:nginx-full:rwx** - Default ACL, so new files/directories inside `/srv/log/nginx/` inherit ACL permissions.

> Default ACL is important to set for directories, 
> so new files/directories inside `/srv/log/nginx/` inherit ACL permissions.

#### Verify access

```bash
getfacl /srv/log/nginx/
```

#### Test the setup

1. Create log entry as user `nginx-full`  (should work)

```bash
sudo -u nginx-full bash -c 'echo "Log Entry 1"  > /srv/log/nginx/access.log'
```

2. Check permissions with `ls` and `getfacl`

```bash
ls -l /srv/log/nginx/access.log
```

You can see, that file belongs to `nginx-full:nginx-full` and permissions are `rw-rw----+`

NOTE: **[+] is added on attribute, which shows ACL is present here **

```bash
getfacl /srv/log/nginx/access.log
```

3. Read log as user `nginx-full` (should work)

```bash
sudo -u nginx-full bash -c 'cat /srv/log/nginx/access.log'
```

4. Read log as user `nginx-read` (should work)

```bash
sudo -u nginx-read bash -c 'cat /srv/log/nginx/access.log'
```


5. Write log as user `nginx-read` (should fail)

```bash
sudo -u nginx-read bash -c 'echo "Log Entry 2"  >> /srv/log/nginx/access.log'
```

6. Read log as user `nginx-write` (should fail)

```bash
sudo -u nginx-write bash -c 'cat /srv/log/nginx/access.log'
```

7. Write log as user `nginx-write` (should work)

```bash
sudo -u nginx-write bash -c 'echo "Log Entry 3"  >> /srv/log/nginx/access.log'
```

8. User `nginx-write` also can move/rename/delete that file (without looking inside)

```bash
sudo -u nginx-write bash -c 'mv /srv/log/nginx/access.log  /srv/log/nginx/access.log.0'
```

```bash
ls -l /srv/log/nginx
```

```bash
sudo -u nginx-write bash -c 'rm /srv/log/nginx/access.log.0'
```

```bash
ls -l /srv/log/nginx
```
